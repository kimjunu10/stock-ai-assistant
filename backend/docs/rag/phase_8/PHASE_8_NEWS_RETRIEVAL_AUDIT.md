# Phase 8 뉴스 검색 실패 원인 감사

브랜치: `phase/8-news-retrieval-audit` (base: PR #63 머지 후 main)

이번 라운드는 개발셋 뉴스 평가 19문항 중 미적중 9문항(news-04, 09, 10, 11,
13, 14, 15, 18, 19)의 근본 원인만 분석했다. 제품 코드·Retriever 설정·
프롬프트·Tool schema·devset·gold label·Validator·Grader는 전혀 수정하지
않았다. 전체 120문항·홀드아웃 40문항은 실행·열람하지 않았다. 대화형 LLM은
호출하지 않았고, `search_news` Retriever(`rag_search_hybrid` RPC)만 임베딩
API를 통해 읽기 전용으로 재현했다(운영 데이터 쓰기 없음).

**중요한 방법론적 유의사항**: news-10/18은 재현 쿼리의 참조일(07-26 vs
07-27)에 따라 gold가 top8 안에 있기도, 없기도 했다. 참조일과 무관하게
**저장된 실제 실행 결과(1차 근거)에는 gold가 없었다**는 사실은 확정적이나,
재현이 이를 완전히 재현하지 못한 원인(참조 시각 미세 차이 또는 임베딩
API의 비결정성)은 확정하지 못했다. 다만 관련 클러스터(6974/6944)와
중복 클러스터(7167/7222/7193)가 모두 재현 쿼리의 top8 근방에서 서로
근접한 점수로 경쟁하고 있었다는 사실 자체가, "같은 사건이 여러 클러스터로
쪼개져 서로의 순위를 갉아먹는" 구조적 문제를 뒷받침한다.

**핵심 발견**: news-11, news-13, news-15 **3건은 devset gold_sources의
`note` 필드(`rag_documents.id=...`)가 가리키는 문서가 현재 `is_current=false`
(비현행)다.** 청크 자체(`is_active`)는 news-11/13은 여전히 `true`이지만
부모 문서가 비현행이라 `rag_search_hybrid`의 `base` CTE 조건
(`is_active=true AND is_current=true`)에 의해 **구조적으로 검색 결과에
나타날 수 없다.** news-15는 청크마저 `is_active=false`다. 세 사건 모두
같은 클러스터ID에 대해 **현행 버전 문서가 별도로 존재**하며(예: 7168의
현행 문서는 `f23dee8c-...`, gold가 가리키는 것은 `aba91639-...`), devset
라벨 작성 시점 이후 뉴스 요약 파이프라인이 해당 클러스터를 재처리해 새
문서 버전을 만들면서 이전 버전이 자연스럽게 비현행 처리된 것으로 판단한다
(코드 버그가 아니라 devset 라벨이 특정 시점의 스냅샷을 가리키는 근본적
한계).

(같은 문항이 여러 범주에 동시에 해당하므로 합계가 9를 넘는다 — 예:
news-13은 "데이터·색인 누락 아님"이지만 "lexical 실패 + 순수 의미 검색
한계"의 복합 원인이다.)

**질문에 대한 답**:

- **8개 Retriever 실패 중 공통 코드 버그가 있는가?** 코드 버그로 볼 만한
  것은 없다. 날짜 필터(news-04/09)는 `_inclusive_end` 등 이미 PR #59에서
  수정된 로직이 정확히 동작한 결과이고("최근 3일"이라는 정의 자체가 이
  사건들을 포함하지 않는 것뿐), 나머지는 뉴스 클러스터링 파이프라인의
  중복 생성 또는 순수 의미 검색 한계다.
- **하나의 최소 수정으로 여러 실패를 해결할 수 있는가?** 아니오. 원인이
  최소 4갈래(날짜 정의, 클러스터 중복, gold 비현행, 검색어 일반성)로
  나뉘어 있어 단일 수정 대상이 없다.
- **top-k 조정 없이 해결 가능한가?** news-10/18/19는 top-k를 늘려도 근본
  해결이 안 된다 — gold와 별개로 존재하는 "더 그럴듯한" 중복/후속
  클러스터가 계속 경쟁하기 때문이다. news-04/09는 top-k와 무관하게 날짜
  필터 자체에서 이미 배제된다.
- **reranker가 실제로 필요한 유형인가?** 아니다. news-10/18/19의 문제는
  랭킹 알고리즘의 정밀도가 아니라 **동일 사건이 여러 클러스터로 중복
  색인된 데이터 문제**다. reranker를 얹어도 "정답이 아닌 것이 더 정답처럼
  보이는" 근본 원인은 해결되지 않는다.
- **gold 자체가 현재 데이터와 불일치한 사례가 있는가?** 있다.
  news-11/13/15 3건은 devset 라벨이 비현행 문서를 가리킨다.
- **같은 사건의 다른 클러스터를 정상 반환한 사례가 있는가?** 있다.
  news-10(레이도스 계약 → 7167/7222), news-13(구글 협업 AI 안경 →
  7195), news-18(한미 조선협력센터 → 7193), news-19(재산분할 확정 →
  이전 단계 클러스터 5600/5604/5611/7011) — **4건**이 "본질적으로 관련된
  다른 문서"를 반환했다.

## 6. 결론

**B. 검색 모델 한계 + C. gold·데이터 문제(공통 구현 오류 아님)**로
결론짓는다. 세부 근거:

### B — 검색 모델 한계 (news-13, news-15, news-19 일부, news-10/18/19의 클러스터 중복)
- 병목: **lexical 후보 생성**(word_similarity/ILIKE 기반)이 질문의 일반
  어휘("SK", "최태원")나 사건 어휘 차이("구글과 협업" vs "AI 안경")에서
  거의 항상 실패하고, semantic도 순위 50~150위권으로 유의미하게 상위에
  올리지 못한다.
- reranker/query expansion이 필요한 이유: 위와 같이 어휘 차이가 큰
  경우에는 순수 임베딩 유사도만으로 상위권 진입이 어렵다. 다만 이번
  9건 중 진짜 순수 랭킹 문제(중복 클러스터·비현행 문제가 전혀 없는 케이스)
  는 사실상 없어, reranker 도입의 ROI가 이 9건만으로는 입증되지 않는다.
- 현재 Phase에서 한계로 남길 수 있다: 그렇다. 이 실패들은 top-k·RRF
  가중치·reranker 어느 것으로도 근본 해결되지 않으며, 뉴스 클러스터링
  파이프라인(별도 시스템, Phase 8 Retriever 범위 밖)의 중복 생성 문제가
  선행 해결돼야 한다.

### C — gold·데이터 문제 (news-04, news-09, news-11, news-13, news-15)
- 실제 제품 실패가 아닌 근거: news-04/09는 devset이 "최근"이라는 상대
  기간 정의(3일)로 07-22 사건을 조회하도록 요구하지만, 실행 시점(07-27)
  기준 그 사건은 이미 5일 전이라 "최근"의 정의상 정당하게 제외된다 —
  질문·기간 정의와 데이터 나이의 자연스러운 불일치다. news-11/13/15는
  gold 라벨이 devset 작성 시점의 스냅샷(당시 현행 문서)을 가리키는데,
  이후 파이프라인이 재처리해 새 버전을 만들면서 라벨이 가리키는 문서가
  비현행이 됐다 — Retriever 코드가 절대 검색할 수 없는 문서를 정답으로
  요구하는 상태다.
- **gold 변경은 이번 PR에서 하지 않는다**(prompt.md 금지 사항 확인).

질문별 키워드 하드코딩은 제안하지 않았다.
