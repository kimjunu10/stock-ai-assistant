## 1. 수정한 실제 근본 원인

문서의 추정을 따르지 않고 원시 Tool 결과와 코드를 직접 확인해 원인을 특정했다.

### ① 유니코드 정규화 불일치 (가장 큰 원인)

```
DB publisher : NFD(자모 분리) — "미래에셋증권" len 15
모델 답변    : NFC(완성형)   — "미래에셋증권" len 6
```

눈에는 같지만 코드포인트가 달라 `b not in evidence.brokers` 가 항상 참이었다.
검증기는 이를 "환각한 증권사"로 보고 **목표주가 문장을 통째로 삭제**했다.

baseline 에서 "검색 실패"로 분류됐던 리포트 12건 중 9건이 실은 이 문제였다.
검색은 정답 리포트를 정확히 찾아놓고 있었다.

같은 결함이 **검색 계층에도** 있었다 — `ResearchReportSearch` 의 broker 필터가
`broker in h.broker` 로 비교해, "IBK투자증권 리포트"가 0건을 반환했다.

### ② Tool 열거형 인자에 유효값이 없음

`event_types: list[str]` 이라 모델이 한국어("배당")를 넣었고, DB 값은
`dividend_matter` 라 `no_data` 가 났다. 배당 공시가 603건 있는데 "없다"고 답했다.

### ③ '단독'을 별도재무제표로 오해

"3분기 단독 영업이익"의 '단독'은 *누적이 아닌 3개월치*인데 `fs_div=OFS`(별도)로
해석했다. DB 에는 CFS 만 있어 조회가 비었다.

### ④ 채점기가 질문에 없는 낱말을 요구

`expected_period.amount_type="누적"` 을 답변 문자열에서 찾았다. "연간 매출액" 질문에
"누적"이라고 쓸 이유가 없는데 11문항이 실패 처리됐다.

### ⑤ 성격이 다른 검색을 한 지표에 혼합

뉴스·리포트(순위 기반)와 용어·재무·공시(정확 행 조회)를 같은 Recall 분모에 넣어
어느 계층을 고쳐야 할지 알 수 없었다.

## 2. 검증기 오탐 수정 결과

**A. 증권사명 검증** — `_norm_name()` 추가(NFC 통일 + 공백 제거).
수집·검증·삭제 판정 세 지점 모두 적용. 그 이상 느슨하게 비교하지 않는다.

**B. 리포트 숫자 검증** — Tool 결과에 `target_price_status='stated'` 인 목표주가가
있으면 근거로 인정된다(①이 원인이었으므로 별도 로직 추가 없이 해소).
Tool 결과에 없는 목표주가는 계속 차단.

**C. 일반 숫자 오탐** — `_strip_non_claim_numbers()` 로 사실 주장이 아닌 숫자를 제외:
가정·예시 문맥("예를 들어"), 페이지·건수, 종목코드(앞뒤 어순 모두), 날짜·연도.
회사 실적·목표주가·주가·금액 주장만 검증 대상으로 남긴다.

### 계속 차단되는 것 (회귀 테스트로 고정)

| 항목 | 결과 |
|---|---|
| 근거에 없는 증권사 | 차단 유지 |
| Tool 결과에 없는 목표주가 | 차단 유지 |
| `stated` 아닌 목표주가를 근거로 인용 | 차단 유지 |
| 근거 없는 회사 재무 숫자 | 차단 유지 |
| 예시 문장 뒤에 숨긴 진짜 환각 | 차단 유지 |

## 3. 공시 enum 계약

DB `structured_disclosures.event_type` 실제 값 9개만 `Literal` 로 노출했다.

```
dividend_matter · treasury_stock_status · treasury_stock_acquisition ·
treasury_stock_disposal · stock_total_status · capital_change_status ·
paid_in_capital_increase · overseas_listing · overseas_listing_decision
```

- 인자 description 에 사용자 표현 → 코드 대응 명시
  (배당·주당배당금 → `dividend_matter`, 자사주 매입 → `treasury_stock_acquisition` …)
- "한국어 값을 넣지 말 것" 명시
- 허용되지 않은 값은 **`no_data` 가 아니라 입력 오류**로 구분
  (`no_data` 로 뭉개면 모델이 "공시가 없다"고 잘못 답한다)
- DB 값과 스키마가 어긋나면 테스트가 깨지도록 고정

질문별 if 문·종목별 하드코딩은 추가하지 않았다.

## 4. 재무 기간·단독·별도 계약

Tool description 과 시스템 프롬프트에 명문화했다.

```
특정 지표 질문 → account_name 필수
연간/사업보고서 → report_period=annual, amount_type=cumulative
누적 → cumulative
단독/당기/3개월 → quarter          ← 별도재무제표가 아니다
자산·부채·자본 → point_in_time
"별도 기준/별도재무제표" 명시 → fs_div=OFS
그 외 → CFS(연결)
no_data 시 다른 기간으로 대체 금지
```

**모호 질문 정책**: "3분기 영업이익"처럼 누적/3개월이 모두 가능한 표현은 한쪽을
몰래 강제하지 않는다. `amount_type` 을 비워 호출하고, 확정되지 않으면 사용자에게
누적인지 3개월치인지 되묻는다.

## 5. 평가 지표 분리

```
retrieval:
  document_retrieval:   recall_at_k · hit_at_1 · mrr · page_accuracy   (뉴스·리포트)
  structured_lookup:    row_hit_rate                                   (용어·재무·공시)
  other_stock_contamination_rate                                        (공통)
```

**Retriever 실패로 세지 않는 경우**(§4):
- Tool 은 정답 문서를 반환했는데 검증기가 답변을 삭제한 경우
- 라벨이 한 청크만 허용했지만 같은 정답 문서의 다른 유효 청크를 반환한 경우

**계속 실패로 남기는 경우**: 다른 종목·엉뚱한 문서를 반환한 경우.

치명적 오류는 **중복 계수**와 **고유 문항 수**를 따로 표시하도록 했다.

## 7. Targeted regression

baseline 실패 파일에서 관련 유형 문항을 자동 추출(중복 제거) → **65문항**.

대상 유형: `answer_dropped_by_validator` · `unsupported_number` ·
`tool_enum_value_unknown` · `number_or_period_error` · `tool_argument_error` ·
`label_gold_id_too_strict`

### 수정 전 → 후 (같은 65문항 기준)

| 지표 | 전 | 후 |
|---|---:|---:|
| 검증기가 답변 삭제 | 22 | **3** |
| 근거 없는 숫자 오탐 | 5 | **2** |
| 증권사 환각 오판 | 22 | **3** |
| `no_data` 발생 문항 | 13 | **4** → 추가 수정 후 **0** |
| 재무 숫자 정확 일치 | 11 | **13** |
| 기간 정확도 통과 | 15 | 15 |

소요 273초.

### 남은 3건은 오탐이 아니라 정탐

`mix-09` · `mix-10` · `mix-14` 에서 모델이 실제로 근거에 없는 목표주가
(140,000원 · 130,000원 · 77,700원 등)를 만들어냈고 검증기가 정확히 차단했다.
`report-12` 는 리포트의 전망 수치를 인용한 경우로, 숫자 근거 판정 정책 논의가 필요하다.

### regression 이후 추가 반영분 재확인

broker 정규화와 '단독≠별도' 프롬프트 수정은 regression 실행 뒤에 들어가, 해당
4문항만 재실행해 확인했다.

| 문항 | 전 | 후 |
|---|---|---|
| `report-05` | no_data → "목표주가 확인 불가" | 키움증권 한화오션 **144,000원**(2026-07-15) 정상 |
| `report-10` | no_data → "리포트 확인 불가" | IBK투자증권 SK하이닉스 매수 **4,000,000원** 정상 |
| `fin-04` | `fs_div=OFS` → no_data | `CFS`+`quarter` → **12.17조원** 정상 |

## 11. 전체 개발셋 120문항 재실행 가능 여부

**가능하다. 권장한다.**

이번 교정으로 baseline 수치를 왜곡하던 요인이 제거됐다.

- 검증기 오탐 22건 → 3건(정탐)
- 공시 `no_data` 9건 해소
- 검색 지표가 문서 검색 / 구조화 조회로 분리돼 해석 가능
- 라벨·채점기 오류 12건 내외 해소

지금 재실행하면 **검색 성능을 왜곡 없이 측정**할 수 있고, 그 결과가 다음 라운드
(검색 튜닝·뉴스 재색인)의 기준선이 된다.

**홀드아웃은 여전히 실행하면 안 된다** — 개발셋 재측정 → 검색 튜닝 →
개발셋 재측정이 끝난 뒤 마지막에 1회만 쓴다.
