**운영 코드는 변경하지 않았다.** `app/agent`, `app/services`, `app/api` 무수정.

### 운영 응답으로 잴 수 없어 우회한 항목

`/api/qa` 응답과 `AgentQaResult` 는 **Tool 입력 인자**와 **기능별 지연시간**을 노출하지 않는다
(`AgentToolCall` 은 `name`·`status`·`result_count` 뿐이고, `ToolTrace.latency_ms` 는 필드만 있고
값이 채워지지 않는다). 운영 코드를 고치는 대신 평가 계층에서 `ToolCallRecorder` middleware 를
얹어 관찰한다. 이 middleware 는 운영 `build_agent` 체인에 등록되지 않는다.

## 4. 정답 라벨 생성 방식

**RAG 가 생성한 답변을 정답으로 쓰지 않았다.** 전부 원본·구조화 기준 데이터에서 만들었다.

| 유형 | 정답 출처 | 확정 방식 |
|---|---|---|
| 금융용어 | `rag_terms` | 표제어 실재 확인(`is_active=true`), `term:{표제어}` |
| 재무 | `financials` | **값을 라벨에 적지 않는다.** `expected_financial` 로 기준행만 지정하고, 채점 시 Tool 과 동일 경로로 DB 재조회 |
| 공시 | `structured_disclosures` | 실제 접수번호(`rcept_no`) |
| 뉴스 | `news_clusters` | 실제 사건(id·날짜·감성·기사 수) |
| 리포트 | `research_reports` | 실제 리포트(증권사·발행일·목표주가 `stated`) |

재무 정답을 라벨에 숫자로 박지 않은 이유는 사람이 옮겨 적을 때의 오타가 그대로 정답이 되기
때문이다. 채점기가 `FactsService` 로 기준행을 읽어 대조한다.

### 수동 검토가 필요한 라벨 65건

원본 근거를 확실히 확인할 수 없는 항목은 임의로 채우지 않고 `needs_manual_review` 로 남겼다.

| 유형 | 건수 | 사유 |
|---|---:|---|
| 뉴스 사건·영향 | 25 | 사건 자체(`news_clusters.id`)는 실재 확인했으나, 정답 출처 식별자가 `chunk_id`(uuid)이고 검색 경로에 따라 달라져 사전 확정 불가 |
| 증권사 리포트 | 20 | 리포트 실재·목표주가는 확인했으나, 질문이 특정 chunk 를 지정하지 않아 정답 chunk 식별자 미확정 |
| 복수 기능 혼합 | 20 | 하위 질문마다 정답 문서가 달라 단일 식별자로 확정 불가 |

이 65건은 **필수 기능 호출·제외 조건·숫자 채점에는 그대로 쓸 수 있고**, 검색 Recall 채점에서만
제외된다(식별자가 없는 항목은 분모에 넣지 않는다).

## 5. 개발셋·홀드아웃 구성

- 개발·튜닝용 **120문항**, 최종 홀드아웃 **40문항**
- 유형별 비율을 유지해 분할(유형마다 뒤 25%를 홀드아웃으로) — 난수 미사용, 재현 가능
- 홀드아웃 id 는 `h-` 접두사로 구분
- 검증기가 개발·홀드아웃 간 **id 중복 0건, 질문 문자열 중복 0건**을 확인

규칙(§6): 홀드아웃은 최종 평가 전까지 튜닝에 쓰지 않는다. 홀드아웃 실패를 보고 수정하면
그 질문은 개발셋으로 옮기고 새 홀드아웃 질문을 보충한다. 질문별 예외 코드는 작성하지 않는다.

## 6. 자동 평가 지표

`aggregate()` 가 계산한다. **분모가 0인 지표는 `0.0` 이 아니라 `null`** 로 낸다
(못 잰 것과 0점인 것을 구분하기 위해).

| 영역 | 지표 |
|---|---|
| Agent | 필수 기능 호출률, 금지 기능 호출률, 불필요 기능 호출률, 기능 입력 정확도, 복합 단계 완료율, 동일 호출 반복률 |
| 검색 | Recall@K, Hit@1, MRR, 다른 종목 혼입률, 리포트 페이지 정확도 |
| 숫자 | 숫자 Exact Match, 단위 정확도, 기간 정확도, 거래일 정확도, 실제값·전망값 혼동 수 |
| 답변·출처 | 핵심 사실 포함률, Citation Precision, Citation Coverage, 존재하지 않는 출처 수, 근거 없는 숫자 수, 제외 조건 위반 수, 과도한 인과 단정 수, 답변 불가 질문의 허위 답변 수 |
| 운영 | P50/P95 지연, 평균 기능·모델 호출 수, 질문당 비용 |

판정 원칙(§8):

- **숫자·기간·식별자는 정확 일치.** 단, `43,601,051,000,000` 을 답변이 `43조 6,010억원` 으로
  반올림해 쓰는 표기 차이는 인정한다.
- **자연어는 완전 일치를 강요하지 않는다.** 핵심어 70% 이상 등장으로 판정한다.
- 제외 조건 위반은 문장 단위로 본다. `"실적 관련 내용은 제외했습니다"` 처럼 부정·제외 표현과
  같은 문장에 있으면 위반으로 세지 않는다(dry-run 에서 실제로 잡힌 오탐을 고친 것).

## 7. 사람 평가 항목

평가자 2명이 독립적으로 기록하도록 CSV 를 평가자별로 따로 만든다(1~5 척도).

1. 질문에 직접 답했는가
2. 핵심 사실이 원본과 일치하는가
3. 중요한 정보를 누락하지 않았는가
4. 근거 없는 내용을 만들지 않았는가
5. 초보자가 이해하기 쉬운가
6. 출처가 주장을 실제로 뒷받침하는가
7. 투자 추천·과도한 인과 단정으로 보이지 않는가

각 행에 질문·답변·제시된 출처·정답 근거(라벨)를 함께 실어 대조할 수 있게 했다.

SSE 계약(`mix-01`): `agent_start → tool_start/tool_end ×2 → sources → delta → done` 순서 확인.

### dry-run 이 실제로 잡은 결함 3건 (모두 평가 코드 쪽, 운영 무관)

1. **제외 조건 오탐** — `"실적 관련 내용은 제외했습니다"` 를 위반으로 셈 → 문장 단위 부정 판정 추가
2. **재무 정답 미연결** — `expected_financial` 이 채점기에 연결돼 있지 않아 숫자 Exact Match 가
   항상 `0/0` 이었음 → `FactsService` 재조회 경로 연결
3. **재무 정답 식별자 형식 오류** — 라벨에 `.../누적` 으로 적었으나 실제 `source_key` 는
   `.../cumulative` → 실제 형식에 맞춤(검색 Recall 0.33 → 0.67)

### 미해결로 남긴 관찰 1건

`term-01`(공매도 설명)에서 검증기가 `"답변에 재무성 숫자가 있으나 이를 뒷받침하는 숫자 Tool
근거가 없음"` 을 냈다. 용어 설명에 포함된 예시 숫자를 재무 수치로 본 것으로 보인다.

동일 패턴이 반복되는지 확인이 필요하다.
