# Phase 8 문제·해결 정리

Phase 8 진행 중 실제로 발생한 문제와 어떻게 해결했는지 정리한다.
"무엇이 잘못 보였는가 → 진짜 원인은 무엇이었는가 → 어떻게 고쳤는가" 순서로 적는다.

## 1. 리포트 목표주가를 찾고도 "확인할 수 없다"고 답함 ★가장 컸던 문제

**증상**
"미래에셋증권에서 SK하이닉스 목표주가 얼마로 봤어?" 라고 물으면
`일부 증권사의 구조화된 목표주가를 확인할 수 없어 해당 수치는 제외했습니다` 로 끝났다.
리포트 15문항 중 12건에서 같은 일이 벌어졌다.

**처음 의심한 것 (틀림)**
검색이 리포트를 못 찾는다고 봤다. 실제로 baseline 지표에서도 리포트 Recall 이 0.125 로
최악이었다.

**실제 원인**
검색은 정상이었다. 출처에 `미래에셋증권 2026-07-14 p.8` 이 정확히 들어와 있었다.
문제는 **유니코드 정규화**였다.

```
DB publisher : NFD (자모 분리) — len 15
모델 답변    : NFC (완성형)   — len 6
```

눈에는 똑같은 "미래에셋증권"이지만 코드포인트가 달라 `b not in evidence.brokers` 가
항상 참이 됐다. 검증기는 이를 "환각한 증권사"로 보고 목표주가 문장을 통째로 삭제했다.

**해결**
`app/agent/validator.py` 에 `_norm_name()` 을 추가해 비교 직전에 NFC 로 정규화했다.
수집(`collect_evidence`)·검증(`validate_answer`)·삭제 판정(`_is_hallucinated_sentence`)
세 지점 모두에 적용했다.

느슨하게 비교하지 않았다 — NFC 통일 + 공백 제거까지만 한다. 근거에 없는 증권사와
근거에 없는 목표주가는 그대로 차단된다(회귀 테스트로 고정).

**교훈**
지표가 "검색 실패"를 가리켜도 원시 출처를 직접 열어봐야 한다. 겉보기 원인만 보고
검색을 튜닝했으면 엉뚱한 곳을 고쳤을 것이다.

## 2. 배당 공시가 603건 있는데 "공시 정보를 확인할 수 없다"

**증상**
"현대차 배당금 얼마야?" → `구조화된 공시 정보를 확인할 수 없습니다`
공시 유형 Recall 0.067 로 전 유형 최저.

**실제 원인**
Agent 가 `get_disclosure_values(event_types=['배당'])` 로 호출했다.
DB 의 실제 값은 `dividend_matter` 다.

```python
event_types: list[str]   # ← 유효값이 어디에도 없음
```

타입이 그냥 `list[str]` 이라 모델이 한국어로 추측했고, 조회가 비어 `no_data` 가 났다.
그러면 모델은 "공시가 없다"고 답한다 — 데이터는 603건 있는데.

**해결**
1. `DisclosureEventType` Literal 로 DB 실제 값 9개만 허용
2. 인자 description 에 사용자 표현 → 코드 대응표 명시
   (배당 → `dividend_matter`, 자사주 매입 → `treasury_stock_acquisition` …)
3. 허용되지 않은 값은 **`no_data` 가 아니라 입력 오류**로 구분
   — `no_data` 로 뭉개면 모델이 "없다"고 잘못 답하기 때문

DB 값과 스키마가 어긋나면 테스트가 깨지도록 고정했다.

## 3. 용어 설명의 예시 숫자를 "근거 없는 재무 숫자"로 오탐

**증상**
"공매도 쉽게 설명해줘" 답변에 검증 오류가 붙었다.

```
예를 들어, 주당 15,000원에 빌린 주식을 10,000원에 사서 갚으면 …
→ "답변에 재무성 숫자가 있으나 이를 뒷받침하는 숫자 Tool 근거가 없음"
```

지원하지 않는 종목 답변도 마찬가지였다.
`"999999" 종목 코드는 지원하지 않습니다` → 999999 를 재무 숫자로 오인.

**실제 원인**
숫자 검증이 날짜만 제외하고 있었다. 종목코드 정규식은 `0` 으로 시작하는 코드나
"종목코드" 뒤에 오는 경우만 잡아서, 코드가 앞에 오면 놓쳤다.

**해결**
`_strip_non_claim_numbers()` 로 확장해 **사실 주장이 아닌 숫자**를 검증 대상에서 뺐다.

- 가정·예시 문맥 문장("예를 들어", "가령", "만약")
- 페이지·건수·개수
- 종목코드(앞뒤 어순 모두)
- 날짜·연도(기존)

회사 실적·목표주가·주가·금액을 사실로 주장하는 숫자만 남긴다.
**근거 없는 재무 주장은 계속 차단**되고, 예시 문장 뒤에 진짜 환각이 있어도 잡는다.

## 4. 정답을 맞혔는데 채점기가 틀렸다고 함

**증상**
`fin-02` "삼성전자 2025년 연간 매출액" → "333.61조원" (DB 값과 일치)
그런데 `period_ok=False`.

**실제 원인**
라벨의 `expected_period.amount_type="누적"` 을 **답변 문자열에 있는지**로 검사했다.
질문이 "연간 매출액"인데 답변에 "누적"이라고 쓸 이유가 없다.
11개 문항이 같은 이유로 실패 처리됐다.

**해결**
라벨을 바꾸지 않고 **채점기**를 고쳤다. 질문에 없는 낱말을 답변에 요구하지 않는다.

```python
tokens = [t for t in (...) if t and (t in case.question or t in record.answer)]
```

틀린 연도를 말하면 여전히 잡힌다(회귀 테스트로 고정).

## 5. 질문 자체가 모호했던 경우

**증상**
`fin-03` "2025년 삼성전자 3분기 영업이익 얼마나 나왔어?"
라벨은 3분기 **누적**(23.5조), Agent 는 3분기 **단독**(12.17조) 답변.

**판단**
둘 다 옳다. 두 값 모두 `financials` 에 실재한다.

```
cumulative  23,527,391,000,000
quarter     12,166,062,000,000
```

**해결**
점수를 올리려고 라벨을 바꾸지 않았다. 대신 **객관적으로 모호한 질문**으로 분류하고
`acceptable_financials` 로 다중 정답을 허용했다. 변경 근거를 `label_basis` 에 남겼다.

같은 방식으로 처리할 수 있는 문항이 더 있는지 전수 검사했고, 모호한 것은 이 1건뿐이었다.

또한 Tool description 에 정책을 명문화했다 — "3분기 영업이익"처럼 누적/3개월이 모두
가능하면 한쪽을 임의로 고르지 말고 `amount_type` 을 비워 호출하고, 확정되지 않으면
사용자에게 되묻는다.

## 6. "단독"을 별도재무제표로 오해

**증상**
`fin-04` "삼성전자 2025년 3분기 단독 영업이익" → `fs_div='OFS'` 로 호출 → `no_data`

**실제 원인**
"단독"은 *누적이 아닌 3개월치*라는 뜻인데 Agent 가 *별도재무제표*로 해석했다.
DB 에는 CFS(연결)만 적재돼 있어 조회가 비었다.

**해결**
Tool description 에 명시적으로 구분했다.

```
"단독", "당기", "3개월" → amount_type=quarter   (fs_div 는 CFS 유지)
"별도 기준", "별도재무제표" → fs_div=OFS
```

## 7. 검색 지표에 성격이 다른 것이 섞임

**증상**
Recall@K 0.333 하나로 뭉뚱그려져 어느 계층을 고쳐야 할지 알 수 없었다.

**실제 원인**
뉴스·리포트(**순위** 기반 문서 검색)와 용어·재무·공시(**정확한 DB 행** 조회)를
같은 분모에 넣고 있었다. 성격이 완전히 다른 실패다.

**해결**
`document_retrieval` 과 `structured_lookup` 으로 분리했다.

추가로, 아래는 Retriever 실패로 세지 않도록 했다(§4 요구):
- Tool 은 정답 문서를 반환했는데 검증기가 답변을 삭제한 경우
- 라벨이 한 청크만 허용했지만 같은 정답 문서의 다른 유효 청크를 반환한 경우

단, **다른 종목을 반환한 경우는 계속 실패**로 남긴다.
치명적 오류도 중복 계수와 고유 문항 수를 따로 표시하게 했다.

## 10. 작업 방식에서 있었던 문제

**평가셋 생성 시 질문 중복**
템플릿을 종목 수보다 적게 만들어 같은 질문이 반복 생성됐고, 개발셋과 홀드아웃에
동일 질문이 들어갔다(분할 원칙 위반). 검증기가 잡아냈고, 실제 사건 제목·증권사명·
발행일을 넣어 구분되게 고쳤다. 조사 오류("공매도**이** 뭐야")도 받침 판정으로 수정했다.

**브랜치 꼬임**
stash 작업 중 다른 브랜치 위에 커밋이 얹혀 남의 커밋이 PR 에 딸려 들어갈 뻔했다.
`main` 위로 cherry-pick 해 내 커밋만 남기고 정리했다.

**토큰 과다 사용**
생성 → 검증을 여러 번 반복하면서 토큰을 많이 썼다. 원인은 처음에 템플릿 설계를
잘못한 것이라, 한 번에 제대로 만들었으면 줄일 수 있었다.
