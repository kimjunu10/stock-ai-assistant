## 1. 뉴스 색인 정합성 — round2 진단 정정

### round2가 내렸던 결론

> 뉴스 Retriever 실패 15건 중 14건(93%)이 `is_current=false` 문서의 활성 청크와 연결됨.

### 실제로 확인한 사실

검색 RPC 정의를 직접 떠서 확인했다.

```sql
-- rag_search_hybrid / rag_search_semantic 공통 base CTE
from public.rag_chunks c
join public.rag_documents d on d.id = c.document_id
where c.is_active = true
  and d.is_current = true      -- 비현행은 애초에 검색되지 않는다
```

**두 RPC 모두 `is_current=true`를 이미 강제한다.** 비현행 청크는 검색 결과에 나올 수 없다.
또 실패 15건의 gold 클러스터는 **전부 현행 문서가 정확히 1개**였다(중복 검색 경로 없음).

즉 "비현행 청크 941건"과 "뉴스 검색 실패"는 **같은 시기에 존재했을 뿐 인과관계가 아니었다**.
round2의 93%는 상관관계를 인과로 읽은 오진이다.

### 진짜 원인 — 종료일 경계에서 당일 뉴스가 잘림

실패 문항의 Tool 인자는 대부분 `relative_period="recent"`였고, 이는 다음으로 풀린다.

```
recent → date_from="2026-07-24", date_to="2026-07-26"   # "오늘까지 포함"
```

그런데 RPC 필터는 `c.published_at <= filter_to`이고, 날짜만 있는 문자열은
timestamptz 로 **그 날 00:00** 이 된다.

```sql
'2026-07-26'::timestamptz                                  → 2026-07-26 00:00:00+00
'2026-07-26T04:30:00+00'::timestamptz <= '2026-07-26'      → false   -- 당일 뉴스 탈락
```

뉴스 청크는 **3,466/3,494(99%)** 가 실제 발행 시각을 갖는다(리포트는 4,350건 전부 자정이라 무관).
그 결과 같은 조건에서 검색 후보가 **296 → 218건(당일 78건, 26% 소실)** 로 줄었다.
gold 사건은 전부 당일(07-26)이었으므로 **구조적으로 찾을 수 없었다.**

`list_recent_news`(주제 없는 조회 경로)는 이미 `T23:59:59` 보정을 하고 있었고,
**하이브리드 검색 경로에만 이 보정이 빠져 있었다.**

### 수정

`app/rag/retrieval.py` 에 공용 헬퍼를 두고 두 경로에 같은 규칙을 적용했다.

```python
def _inclusive_end(date_to: str | None) -> str | None:
    """종료일(YYYY-MM-DD)을 그 날 끝까지 포함하도록 보정한다."""
    if date_to and len(date_to) == 10:
        return f"{date_to}T23:59:59+09:00"
    return date_to     # 시각이 이미 있으면 사용자가 지정한 경계이므로 그대로 둔다
```

임베딩·RRF·top-k·reranker는 건드리지 않았다.

즉시 실측한 효과(수정 전 0/3 → 수정 후 3/3, gold가 1~2위로 상승):

| 질의 | 수정 전 | 수정 후 |
|---|---|---|
| 갤럭시Z 폴드8 (gold 7189) | 미검색 | **1위** |
| 구글 AI 협업 (gold 7182) | 미검색 | **2위** |
| 아세안 현대컵 (gold 7194) | 미검색 | **1위** |

### 비현행 활성 청크 정리

검색 결함은 아니지만 색인 상태가 사실과 어긋나 있어 정리했다.

- 스크립트: `scripts/cleanup_stale_news_chunks.py` (dry-run 기본, `--apply` 로만 반영)
- 처리: `is_active=false` 로 내리기만 한다. **hard delete 없음.**
- 보존: 뉴스 원본·`news_clusters`·현행 문서와 그 청크는 건드리지 않는다.

| 구분 | 실행 전 | 실행 후 |
|---|---|---|
| 비현행 문서 | 868 | 868 (삭제 안 함) |
| **비현행 활성 청크** | **945** | **0** |
| 현행 문서 | 3,311 | 3,311 |
| **현행 활성 청크** | **3,494** | **3,494 (불변)** |
| news_clusters | 7,229 | 7,229 (불변) |

2회차 실행은 **대상 0건 / 변경 없음** 으로 idempotent 를 실증했다.

작성 중 발견해 함께 고친 결함 2가지:
- PostgREST 1000행 제한 때문에 통계가 조용히 잘렸다(현행 청크가 3,494 대신 1,071로 집계됨) → 페이지네이션 추가.
- 500건 배치 update 가 statement timeout → update 배치를 50으로 분리.

## 2. Agent Tool 선택·인자 오류

원인별로 묶으면 3가지였고, 질문별 예외 없이 공통 규칙만 고쳤다.

### (A) 복합 질문에서 원인 부분을 재무 숫자로 답하려 함 — 6건

`mix-06~10`, `news-11` 이 모두 같은 형태였다.
"왜 줄었어 / 부진 이유 / 실적 배경 / 무슨 일 있었어" + "증권사 전망" 인데,
원인 부분에 `get_financial_facts` 를 부르고 `search_news` 를 빠뜨렸다.

기존 프롬프트에는 역방향 규칙("원인을 묻지 않았으면 뉴스 검색 하지 말 것")만 있고
정방향 규칙이 없었다. 그 빈틈을 메웠다 (`app/agent/prompts.py`).

```
· "왜 줄었어", "부진 이유", "실적 배경", "무슨 일 있었어"처럼 원인·배경을 묻는 부분은
  재무 수치로 답할 수 없다. search_news 로 사건을 찾아 근거로 쓴다.
  get_financial_facts 는 "얼마인지"에 답할 뿐 "왜 그런지"에 답하지 못한다.
```

결과: 필수 Tool 누락 6 → **0**, 금지 Tool 호출 1 → **0**.

### (B) 종목 지정 규칙이 양방향으로 어긋남 — 2건

정확히 반대인 두 오류가 같이 있었다.

| 문항 | 상황 | 수정 전 | 수정 후 |
|---|---|---|---|
| `na-03` "주가 알려줘" | 문맥 종목 **없음** | 삼성전자를 **임의 선택**해 답변 | **되묻기** |
| `ctx-06` "이 뉴스 나온 회사 주가" | 문맥 종목 **있음**(000660) | 되물음 | **000660 조회** |

프롬프트에 두 방향을 함께 명시했다.

```
- 문맥 종목이 있으면 "이 회사", "이 뉴스 나온 회사", "여기" 같은 지시 표현도 그 종목을
  가리키는 것으로 보고 되묻지 않는다. 바로 Tool 을 호출한다.
- 문맥 종목이 없고 사용자도 종목을 말하지 않았으면, 특정 종목을 임의로 정해 조회하지
  않는다. 어떤 종목인지 되묻는다.
```

### (C) 증권사 지정이 Tool 인자로 전달되지 않음 — 1건

`report-06` "대신증권 SK하이닉스 리포트" 에서 `broker` 인자를 넘기지 않아
교보증권 리포트로 답했다. `broker` 는 **Tool docstring 에 설명이 아예 없었다** —
모델이 쓸 이유를 알 수 없었다. `app/agent/runtime.py` 에 설명을 추가했다.

### 남은 불필요 Tool 호출 4건 (수정하지 않음)

`na-01/04/06/08` 은 답변 불가 질문에 Tool 을 먼저 부르지만,
**답변 자체는 정확하다**("확인할 수 없습니다"). 확인 후 없다고 답하는 것은 합리적 동작이라
프롬프트로 억제하지 않았다. 억지로 막으면 "확인도 안 하고 없다고 답하는" 더 나쁜 행동이 된다.

## 3. 평가기·라벨 잔여 문제

round2가 "평가기·라벨" 로 분류한 16건을 전부 다시 확인했다.

### (A) 중복 계수 — 14건 (분석 스크립트 결함)

`report-01/02/03/04/05/07/09/10/11/12/13/14/15`, `news-18` 은
**정답 문서를 제대로 찾았고**(`report_id` 완전 일치), 라벨이 요구한 특정 페이지 청크 대신
같은 문서의 다른 청크를 반환한 경우였다.

채점기 `grader.py` 는 이를 이미 Retriever 실패에서 제외하고 있었다
(`_doc_miss_is_not_retriever_fault` → 4건 모두 `True` 로 실측 확인).
**제 round2 분석 스크립트만 이를 실패로 한 번 더 셌다.** 스크립트를 고쳤다.

재집계 결과: 실패 **47 → 35건**, 무결점 **73 → 85건**.
(제품이 좋아진 게 아니라 잘못 센 것을 바로잡은 값이다.)

### (B) 부르지 않은 대안 Tool 의 인자를 채점 — 1건

`disc-11` 은 `required_tools_any: [get_disclosure_values, search_disclosures]` 인데
`expected_args` 에는 `get_disclosure_values` 만 적혀 있었다.
Agent 가 허용된 `search_disclosures` 로 답했는데, 부르지도 않은 Tool 의 인자가 실패로 잡혔다.

`grade_arguments()` 를 고쳤다 — **허용된 대안 Tool 을 실제로 쓴 경우에만** 채점에서 제외한다.
필수 Tool 을 아예 안 부른 경우는 그대로 실패로 남는다(느슨해지지 않음, 테스트로 고정).

### 라벨을 바꾸지 않은 것

정답(gold)은 **하나도 수정하지 않았다.** 점수를 올리기 위한 라벨 변경은 없다.
실제 제품 실패인 사례(뉴스 검색 순위, 리포트 검색 품질)는 실패로 그대로 남겼다.

## 4. 리포트 Retriever 실패 2건 — 이번 PR에서 수정하지 않음

| 문항 | 질문 | 관찰 |
|---|---|---|
| `report-06` | 대신증권 SK하이닉스 리포트 전망 | `broker` 인자 미전달 → 교보증권 답변 (§2-C 로 설명 보강) |
| `report-08` | IBK투자증권 삼성전자 리포트 요약 | `broker` 필터는 정상. gold(07-08) 대신 오래된 05-04 반환 |

`report-08` 을 파고들어 확인한 것:

- gold 리포트 `3d0d8a91`(IBK, 07-08)은 **정상 색인·활성**이다(18청크 전부 active, `is_current=true`).
  ※ 처음에 `source_pk` 로 조회해 "244건 전부 미색인" 이라는 잘못된 결론을 냈으나,
  리포트의 `source_pk` 는 콘텐츠 해시이고 실제 키는 `chunks.source_locator->>'report_id'` 였다. 정정한다.
- 후보 수를 20→160 으로 8배 늘려도 gold 가 후보에 들어오지 않는다(40에서 상한).
- 원인: `"삼성전자"` 같은 밋밋한 쿼리로는 의미 검색이 해당 리포트를 상위로 올리지 못한다.
  `broker` 필터는 **검색 이후 후처리**라(RPC 에 broker 필터가 없음) 후보에 없으면 살릴 수 없다.

이는 **의미 검색 품질 문제**이므로 §4 지침에 따라 기록만 하고 수정하지 않았다.
임베딩·RRF·reranker 변경 금지 범위에 해당한다.

## 5. targeted regression (30문항, 실제 LLM 실행)

대상: 뉴스 Retriever 14 + Agent Tool 선택 13 + Tool 인자 6 + 평가기·라벨 2 + 리포트 2 (중복 제거 30문항).
전체 120문항·홀드아웃은 실행하지 않았다.

```
n=30, 소요 170.9초
뉴스 정답 문서 적중   0 → 9  (대상 14문항)
필수 Tool 누락        6 → 0
Tool 인자 오류        6 → 0
금지 Tool 호출        1 → 0
불필요 Tool 호출      6 → 4
타 종목 혼입          0 → 0
답변 삭제             1 → 1   (안전장치 유지)
근거없는 숫자 차단     2 → 2   (안전장치 유지)
증권사 환각 차단       1 → 1   (안전장치 유지)
```

확인 항목 대조:

| 확인 항목 | 결과 |
|---|---|
| 비현행 뉴스 청크가 검색에서 제외됨 | 충족(RPC 가 원래 강제 + 청크 945건 비활성화 완료) |
| 정답 뉴스 사건 Recall 개선 | 충족 (0 → 9/14) |
| 타 종목 혼입 없음 | 충족 (0 유지) |
| 필수 Tool 누락 감소 | 충족 (6 → 0) |
| 금지·불필요 Tool 증가 없음 | 충족 (금지 1→0, 불필요 6→4) |
| Tool 인자 정확도 개선 | 충족 (6 → 0) |
| 정상 답변을 평가기가 실패 처리하지 않음 | 충족 (중복 계수 14건 제거) |
| 기존 안전 검증 유지 | 충족 (검증기 3종 수치 불변) |
| 기존 전체 테스트 통과 | 충족 (468 passed / 1 failed — 기존 실패) |

### 남은 뉴스 실패 5건

`news-04/09/14/15/19` 는 관련 뉴스는 찾았으나 gold 와 다른 사건을 골랐다.
날짜 경계가 아니라 **의미 검색 순위** 문제이며, `news-15`("SK 건은 어떤 내용이야?") 처럼
질의 자체가 모호한 경우도 있다. §4 와 같은 이유로 이번 PR에서는 수정하지 않았다.

## 7. 개발셋 120문항 재실행 준비 여부

**준비됨.** 근거:

- 뉴스 검색의 구조적 결함(당일 누락)이 제거됐고 회귀 테스트로 고정됐다.
- Tool 선택·인자 오류가 targeted 기준 0건이다.
- 평가기 중복 계수가 제거돼 이제 지표가 실제 실패만 센다.
- 전체 테스트 통과, 검증기 안전장치 수치 불변.

다만 targeted 30문항은 **수정 대상 문항에 편향된 표본**이므로, 개선폭이 전체 120문항에서
그대로 재현된다고 볼 수 없다. 다음 라운드에서 전체 재실행으로 확인해야 한다.
