## 0. 30초 요약

우리는 **주식 정보를 알려주는 AI 챗봇**을 만들었습니다. 이 AI는 상상해서 답하지 않고, **회사 DB에서 실제 자료를 찾아서** 답합니다. 이 방식을 RAG라고 부릅니다.

문제는 "잘 되는 것 같다"는 느낌만으로는 발표할 수 없다는 것이었습니다. 그래서 **질문 160개로 시험지를 만들고**, 여러 번 시험을 치고, 틀린 문제의 원인을 하나씩 찾아 고쳤습니다.

가장 중요한 결과는 두 가지입니다.

- **형식 조건 통과율은 85% → 97.5%로 올랐습니다.** 단, 뒤의 97.5%는 **같은 문제를 다시 푼 결과**입니다.
- **뉴스 검색 정확도는 33.33%에 머물러 있습니다.** 이건 아직 부족한 부분입니다.

이 두 숫자를 섞지 않는 것이 이 문서의 핵심입니다.

## 1. 우리는 왜 이렇게 많은 실험을 했는가?

AI가 그럴듯한 말을 하는 것과 **정확한 자료를 근거로 말하는 것**은 완전히 다릅니다.

처음에는 그냥 써보면서 "괜찮네" 하는 수준이었습니다. 그런데 실제로 확인해 보니 이런 일들이 있었습니다.

- "2025년 영업이익 얼마야?"라고 물으면 **연간 43.60조를 말해야 하는데 3분기 누적 23.53조**를 말했습니다.
- 같은 질문을 두 번 하면 두 번째에는 **"데이터 없음"**이라고 답했습니다.
- 현대차를 물었는데 답변에 **"삼성전자(005380)"**라고 회사 이름을 지어냈습니다.
- 화면에서 삼성전자를 선택한 상태로 애플을 물으면, **삼성전자 숫자를 애플 숫자라고** 답할 수 있었습니다.

이런 문제는 **직접 재보지 않으면 절대 발견되지 않습니다.** 그래서 실험을 반복했습니다.

## 3. 160개 질문은 어떻게 만들었는가?

**DB에 실제로 있는 자료를 보고, 그 자료로 답할 수 있는 질문을 만들었습니다.**

예를 들어 DB에 "삼성전자 2025년 영업이익 43,601,051,000,000원"이라는 행이 있으면, "삼성전자 2025년 연간 누적 영업이익은 얼마야?"라는 질문을 만듭니다.

9가지 유형으로 골고루 나눴습니다.

| 유형 | 개수 | 예시 |
|---|---:|---|
| 금융용어 | 15 | "공매도가 뭐야?" |
| 정확한 재무 숫자 | 25 | "삼성전자 2025년 연간 영업이익 얼마야?" |
| 뉴스 사건·영향 | 25 | "삼성전자 브로드컴 건은 어떤 내용이야?" |
| 공시 설명·구조화 값 | 20 | "이 공시가 왜 중요해?" |
| 증권사 리포트 | 20 | "미래에셋증권에서 SK하이닉스 목표주가 얼마로 봤어?" |
| 복수 기능 혼합 | 20 | "영업이익 얼마고 왜 늘었어?" |
| 부정·제외·대조 | 15 | "실적 얘기는 빼고 뉴스만 알려줘" |
| 현재 화면 문맥 | 10 | "이 종목 목표주가 얼마야?" |
| 답변 불가능·모호 | 10 | "삼성전자랑 애플 실적 비교해줘" (애플 데이터 없음) |
| **합계** | **160** | |

마지막 "답변 불가능" 유형이 중요합니다. **모르는 것을 모른다고 말하는지** 시험하려고 일부러 넣었습니다.

## 4. 120개와 40개는 왜 나눴는가?

**시험 문제를 미리 보고 공부하면 시험이 의미가 없기 때문입니다.**

- **개발셋 120개** — 마음껏 보고, 틀리면 고치는 데 씁니다. "연습 문제집"입니다.
- **홀드아웃 40개** — 다 고친 뒤 **딱 한 번만** 푸는 문제입니다. "실제 수능"입니다.

만약 40개도 보면서 고쳤다면, 점수가 높게 나와도 그건 "답을 외운 것"일 뿐 실력이 아닙니다.

나누는 방법도 재현 가능하게 했습니다. 유형별로 **뒤 25%를 홀드아웃**으로 떼어냈고, 주사위를 굴리지 않았습니다. 홀드아웃 문제는 이름이 `h-`로 시작합니다.

> **정직한 고백**: Phase 9에서 이 40문제를 **다시 썼습니다.** 그래서 지금 이 40문제는 **더 이상 "처음 보는 문제"가 아닙니다.** 원래 규칙은 "홀드아웃을 보고 고치면 새 문제를 보충한다"였는데, 그 보충을 하지 않았습니다. 이것이 97.5%를 실력으로 말할 수 없는 이유입니다.

## 5. 정답은 누가 만들었는가? Claude Code가 임의로 만든 것인가?

**둘 다 아닙니다. 정답은 DB가 만들었습니다.**

핵심은 **AI가 낸 답을 정답으로 쓰지 않았다**는 것입니다. 만약 그렇게 했다면 AI를 AI로 채점하는 셈이라 아무 의미가 없습니다.

| 유형 | 정답을 어디서 가져왔나 |
|---|---|
| 금융용어 | `rag_terms` 테이블에 그 용어가 실제로 있는지 확인 |
| **재무 숫자** | **정답 숫자를 아예 적지 않았습니다** (아래 설명) |
| 공시 | 실제 접수번호(`rcept_no`) |
| 뉴스 | 실제 사건 번호(`news_clusters.id`) |
| 리포트 | 실제 리포트 ID + 목표주가가 본문에 진짜 있는 조각만 |

**재무 숫자를 왜 안 적었나?** 사람이 `43,601,051,000,000` 같은 숫자를 손으로 옮겨 적으면 **오타가 그대로 정답이 되어버립니다.** 그래서 정답 칸에는 "삼성전자 / 2025년 / 연간 / 영업이익 / 연결"처럼 **어느 행을 볼지만** 적고, 채점할 때 DB에서 그 행을 다시 읽어 비교합니다.

Claude Code가 한 일은 **자료를 찾아 대조하고 검증 규칙을 만든 것**이고, 정답 값 자체는 DB에서 나왔습니다.

## 6. 사람이 라벨링한 데이터인가?

**아닙니다. 이 표현을 쓰면 안 됩니다.**

이유는 명확한 증거 3가지입니다.

1. **사람 평가 양식은 만들었지만 아무도 채우지 않았습니다.** `human_review_rater1.csv`를 열어보면 질문·답변·출처는 있지만 **7개 점수 칸이 전부 비어 있습니다.**
2. **원본 문서가 스스로 "양식만 생성"이라고 기록**하고, 사람 평가를 "아직 하지 않은 일"로 분류했습니다.
3. 뉴스 동일 사건 승인 파일의 승인자 칸에 이렇게 적혀 있습니다:
   **`"agent-assisted manual review"`** (= Agent 보조 검토)

### 그럼 정확히 뭐라고 말해야 하나?

> "**DB 원본에서 결정적으로 유도하고, Claude Code/Codex가 원본과 대조해 검증한 정답 데이터**입니다. 독립적인 사람 라벨링은 수행하지 않았습니다."

### 그래도 정답은 믿을 수 있나?

네, **검증 가능하다는 점**에서 믿을 수 있습니다.

- 검증 스크립트가 **24가지 항목**을 확인하고 전부 통과했습니다(정답이 DB에 실제로 있는지, 종목이 일치하는지, 페이지가 PDF 범위 안인지 등).
- **일부러 틀린 정답을 넣어봤습니다.** 존재하지 않는 uuid를 하나 심었더니 검증기가 `[FAIL] 27/28`로 정확히 잡아냈습니다.
- 확인이 안 되는 65건은 **억지로 채우지 않고** "확인 필요"로 남겼다가, 나중에 DB 대조로 하나씩 확정했습니다.

즉 **"사람이 눈으로 봤다"는 보증은 없지만, "기계가 다시 확인할 수 있다"는 보증은 있습니다.**

## 7. 질문 하나를 어떻게 채점했는가?

`fin-01`을 예로 들겠습니다.

**질문**: "삼성전자 2025년 연간 누적 영업이익은 얼마야?"

AI가 답하면 채점기가 이런 항목을 확인합니다.

| 확인 항목 | 이 문항에서는 |
|---|---|
| 필요한 기능을 불렀나? | `get_financial_facts`를 불렀나 |
| 부르면 안 되는 기능을 불렀나? | 뉴스 검색을 부르지 않았나 |
| 기능에 넣은 조건이 맞나? | 종목 005930, 2025년, 연간 |
| 숫자가 정답과 같나? | DB의 43,601,051,000,000과 비교 |
| 기간을 맞게 말했나? | "2025년", "연간" |
| 출처를 지어내지 않았나? | 없는 출처를 만들지 않았나 |
| 다른 회사 자료가 섞였나? | SK하이닉스 자료가 없나 |
| 과하게 단정했나? | "무조건 오른다" 같은 표현이 없나 |

이 항목 **전부 통과하면 pass**, 하나라도 걸리면 fail입니다. 이것을 **"형식 조건 통과(formal pass)"**라고 부릅니다.

### 숫자 비교는 좀 너그럽습니다 (솔직히 말하면)

`43,601,051,000,000`을 AI가 `"43조 6,010억원"`으로 답하면 통과시킵니다. 사람이 읽기 좋게 반올림한 것을 틀렸다고 하면 이상하니까요.

**그런데 이 관용 폭이 생각보다 넓습니다.** 코드를 뜯어보니 1조 이상 금액은 **조 단위로 반올림해서 ±0.5조까지** 통과합니다. 즉 `"43조"`나 `"44조"`도 같은 정답으로 통과합니다. 그래서 `number_exact_match`라는 이름이 붙어 있지만, 큰 금액에 대해서는 **엄밀한 exact가 아닙니다.**

### 자연어 판정은 AI 채점관(Solar)이 합니다

"데이터가 없다"는 뜻의 표현은 수십 가지입니다. 처음에는 `"확인할 수 없습니다"`라는 **단어가 있는지**만 봤습니다. 그러니 뜻이 같은 `"아직 공시되지 않았습니다"`가 틀린 것으로 처리됐습니다.

이게 위험한 이유는 코드 주석에 그대로 적혀 있습니다:

> "그러면 제품 프롬프트를 채점기 키워드에 맞춰 쓰게 되는 역방향 압력이 생긴다(**평가지표를 속이는 것**)."

그래서 뜻을 판단하는 부분만 Solar LLM에게 맡겼습니다. **단, 숫자·기간·기능 호출 같은 객관적으로 확인 가능한 것은 절대 AI에게 맡기지 않았습니다.**

## 8. 각 실험에서 무엇이 문제였고, 어떤 수치가 나와서 무엇을 고쳤는가?

시간 순서대로, 이야기처럼 정리합니다.

### 8-1. 뉴스 검색: "벡터만으로는 이름을 못 찾는다" (Phase 3)

**문제**: 처음에는 뜻이 비슷한 걸 찾는 방식(벡터 검색)만 썼습니다. 그런데 "HBM4", "ADR" 같은 **정확한 이름·약어**를 못 찾았습니다.

**실험**: 검색기만 따로 떼어내 두 방식을 비교했습니다. AI는 관여하지 않았습니다.

| 질문 종류 | 벡터만 | 벡터+키워드 결합 |
|---|---:|---:|
| **정확한 이름 질문** | **25%** | **91.7%** |
| 자연어 문장 질문 | 97.5% | 97.5% (유지) |

**중간에 발견한 것**: 처음 결합 방식은 50%밖에 안 나왔습니다. 원인이 두 개였는데, 하나는 **평가 방법 자체가 틀렸던 것**(질문의 절반이 "SK", "AI" 같은 흔한 조각이었음)이고, 하나는 **검색 코드 결함**(정확히 일치하는 걸 우대하지 않아서 비슷한 것들에 밀림)이었습니다.

**고친 후**: 정확한 이름 찾기가 **50% → 91.7%**. 따로 떼어둔 홀드아웃에서도 **64.7% → 94.1%**로 같은 패턴이 재현됐습니다.

**대가**: 검색이 5배 느려졌습니다(119ms → 607ms). 알고 받아들였습니다.

> 이것이 우리 실험 중 **유일하게 비교 대상(대조군)이 있는 진짜 A/B 실험**입니다.

### 8-2. 반복 질문이 망가진다 (Phase 5.5)

**문제**: 스테이징에서 같은 질문을 두 번 하면 두 번째에 "데이터 없음"이 나왔습니다.

**원인**: 중복 호출을 막는 장치가 **요청이 끝나도 기억을 지우지 않았습니다.** 그래서 두 번째 요청이 "이미 물어본 것"으로 차단됐습니다. 평가 스크립트는 질문이 매번 달라서 이 문제가 안 드러났습니다.

**같이 발견한 것**: "2025년 영업이익"에 **3분기 누적 23.53조**를 답했습니다. 정답은 **연간 43.60조**입니다.

**고친 후**: 두 문제 모두 **4번 중 4번 정확**하게 나왔습니다.

**교훈**: **평가 점수가 좋아도 실제로 써보면 다른 버그가 나옵니다.** 이후 계속 실제 환경 확인을 병행한 이유입니다.

### 8-3. 개발셋 첫 시험: 120문제 중 42개만 무결점 (Phase 8)

**결과**: 8분 44초, 0.55달러. **무결점 42개 / 문제 있음 78개.**

| 항목 | 점수 |
|---|---:|
| 필요한 기능 호출 | 94.5% |
| 기능 조건 정확도 | 87.3% |
| 숫자 정확도 | 73.7% |
| 기간 정확도 | 71.1% |
| 검색 정확도 | 33.3% |

유형별로 보니 **공시가 6.7%, 리포트가 12.5%**로 처참했습니다.

### 8-4. 세 번 고치고 세 번 다시 시험

| 회차 | 무엇을 고쳤나 | 기능조건 | 숫자 | 기간 |
|---|---|---:|---:|---:|
| 1차 | 채점기 오탐, 기능 입력 규칙 | 87.3% → **95.3%** | 73.7% → **94.7%** | 71.1% → **100%** |
| 2차 | 뉴스 검색 종료일 경계 버그 | **100%** | **100%** | 100% |
| 3차 | 공시 정렬, 리포트 검색, 채점기 오탐 | 98.7% | 100% | 100% |

숫자·기간 정확도가 **73.7% → 100%, 71.1% → 100%**로 올라간 것이 이 구간의 성과입니다.

### 8-5. ★ 반전: "점수가 0%인 게 아니라 계산이 틀렸다" (PR #63)

**문제**: 2차 이후 검색 점수가 계속 **0.0**으로 나왔습니다. 검색이 완전히 망가진 것처럼 보였습니다.

**조사**: AI를 다시 돌리지 않고, 저장된 기록만 다시 채점했습니다. 그리고 **채점 코드에 결함 2개**를 찾았습니다.

- **결함 1**: 정답을 **완벽하게 맞힌 문항까지** 계산에서 통째로 빠뜨렸습니다. "이건 검색기 잘못이 아니야"를 판단하는 함수가, "이미 정확히 맞혔다"는 경우를 구분하지 않았습니다.
- **결함 2**: 1등을 판정할 때 **실제 검색 순위가 아니라 ID를 알파벳순으로 정렬한 것**을 봤습니다. `news-01`을 직접 대조해 보니, 정답이 실제로는 1위인데 채점기는 2위를 보고 있었습니다.

**고친 후 진짜 점수**:

| | 잘못된 점수 | 실제 점수 |
|---|---:|---:|
| 뉴스 검색 | 0.0 | **52.6%** |
| **리포트 검색** | 0.0 | **93.3%** |

**의미**: 리포트 검색은 **원래부터 잘 되고 있었습니다.** 앞선 수정이 효과적이었는데 **잘못된 계산이 그 효과를 완전히 가리고 있었습니다.**

> **발표에서 강조할 점**: 우리는 제품만 고친 게 아니라 **채점기 자체도 의심하고 감사했습니다.** 필수 기능 호출률은 손으로 다시 계산해(125/127 = 0.9843) 공식 값과 정확히 일치함을 확인했습니다.

### 8-6. 뉴스가 왜 안 찾아지는지 끝까지 파봤다 (PR #64)

뉴스 19문제 중 9개를 못 찾았습니다. "검색이 나쁘다"로 끝내지 않고 하나씩 재현했습니다.

원인이 **5가지로 갈렸습니다**.

| 원인 | 건수 | 설명 |
|---|---:|---|
| **날짜 필터가 정답을 잘라냄** | 2 | 정답 뉴스가 7월 22일인데, AI가 "최근 3일(7/25~7/27)"로 검색해 **후보 200개에도 안 들어옴** |
| **같은 사건이 여러 개로 쪼개짐** | 3 | 같은 계약 뉴스가 별개 사건으로 색인돼 서로 순위를 깎아먹음 |
| 검색어가 너무 흔함 | 3 | "SK", "최태원" 같은 검색어는 200개 중 46위·82위 |
| **기능을 잘못 골랐음** | 1 | 뉴스 질문인데 뉴스 검색을 아예 안 부르고 재무 조회만 함 |
| 최신순 정렬에서 밀림 | 1 | 정답보다 최신인 사건이 5개 이상 있었음 |

**중복 사건의 공통 원인**: 뉴스를 묶는 코드가 **24시간이 지난 후보를 유사도 계산 전에 무조건 버렸습니다.** 48시간·40시간 차이 나는 같은 사건이 판정 기회조차 못 받고 새 사건으로 등록됐습니다.

**고친 것**: 시간 창을 24 → 48시간으로 늘렸습니다. **단, 유사도 기준은 완화하지 않았습니다** — 후보에 넣어주기만 하고, 합칠지는 여전히 엄격하게 판단합니다.

> **중요**: 뉴스 검색 실패의 다수는 **"검색 엔진이 멍청해서"가 아니라 날짜 필터·데이터 중복 때문**이었습니다.

### 8-7. 개발셋 최종: 97.44% → "코드 동결" (PR #67)

### 8-8. ★★ 수능날: 홀드아웃 85%, 그런데 실제로는 31건이 실패 (PR #72)

드디어 40문제를 처음 풀었습니다. **2분 5초, 0.23달러.**

**결과: 34/40 = 85.00%**

| 항목 | 개발셋 | 홀드아웃 |
|---|---:|---:|
| 통과율 | 97.44% | **85.00%** |
| 뉴스 검색 | 63.16% | **0%** |
| 리포트 검색 | 86.67% | **0%** |
| 구조화 조회 | 77.78% | **0%** |

**거의 모든 검색·조회가 0%**인데 통과율은 85%였습니다. 어떻게 이럴 수 있나?

**실제로는 40문항 중 31건이 실패**했습니다. Tool 오류 36건, 상태 누락 2건, 예산 초과 1건. 그런데 **통과 조건이 "기능을 불렀는가"만 보고 "기능이 성공했는가"는 보지 않아서**, 31건 중 숫자가 틀린 6건만 실패로 집계됐습니다.

> "Phase 8 상태: 제품 성능 완료 판정 **미완료**"

그리고 **낮은 점수를 본 뒤에도 코드·정답·채점기를 고치지 않았습니다.** 점수를 보고 고치면 그 점수는 의미가 없어지니까요.

### 8-9. 원인 추적: 왜 Tool이 다 터졌나 (PR #73)

AI를 다시 돌리지 않고 **저장된 기록만으로** 조사했습니다.

- **상태 누락 2건의 정체**: AI가 `순이익`이라고 썼는데 허용값은 `당기순이익`이었습니다. 입력 검증 오류가 Tool 본문 **전에** 터져서, 오류 처리기가 형식에 맞지 않는 평문을 돌려줬고 기록기가 이를 "알 수 없음"으로 남겼습니다.
- **예산 초과 1건의 정체**: 실패한 호출들이 5회 한도를 다 써버려서 최종 답변 단계에 도달하지 못했습니다.
- **오류 36건**: **원인을 확정할 수 없었습니다.** 과거 코드가 예외를 안전한 경고문으로 바꿔버려 실제 예외가 남아있지 않았습니다. 같은 입력을 지금 코드로 다시 돌려보니 **전부 성공**했습니다.

**정직하게 처리한 부분**: 원인을 모르는데 DB 클라이언트를 바꾸거나 재시도를 늘리는 **추측 수정을 하지 않았습니다.** 대신 **다음에 같은 일이 생기면 정확한 예외를 잡을 수 있도록** 로그를 심었습니다.

**왜 개발셋에서 안 드러났나?** 개발셋에도 이미 상태 누락이 4건 있었습니다. 그런데 **채점기가 Tool 성공 여부를 통과 조건으로 안 써서** 97.44%라는 숫자에 전혀 드러나지 않았습니다.

### 8-11. 뉴스 기간 문제를 끝까지, 그리고 최종 동일 문항 회귀 (PR #75)

뉴스가 왜 33.33%에 머물렀는지 6문항 기록을 다 봤습니다.

**발견**: 6문항 **전부 질문에 기간 표현이 없었는데 AI가 전부 "최근"을 붙였습니다.** "최근"은 3일로 해석되어, 며칠 전 사건이 필터에서 잘려나갔습니다.

- `h-news-22`: 정답 7월 23일 → 7/25~7/27 범위 밖 → 제외
- `h-news-23`, `h-news-24`: 정답 7월 24일 → 같은 이유로 제외

**고친 것**: **사용자가 직접 말한 기간만 적용**하도록 했습니다. 기간 표현이 없으면 필터를 걸지 않습니다.

**하드코딩을 하지 않았습니다**: 코드는 시간 표현만 봅니다. 홀드아웃 문항 번호·뉴스 제목·회사명·인물명·특정 날짜를 **전혀 참조하지 않습니다.**

그 뒤 production smoke를 통과한 뒤에만, **같은 홀드아웃 40문항을 데이터 순서대로 정확히 1회** 다시 실행했습니다. 재시도·외부 장애·개발셋 실행은 모두 0건입니다. 이 실행은 새로운 블라인드 평가나 일반화 성능이 아니라 **Phase 10 제품 수정 후 동일 홀드아웃 최종 회귀**입니다.

- 자동 형식 조건 통과: **39/40 (97.50%)**
- 뉴스 canonical-cluster Recall@K: **2/6 (33.33%)**
- 실제 Tool 실행 성공: **37/39문항**, 최종 답변 완료: **40/40**

기간 정책 수정 뒤 `h-news-22`는 정답 cluster를 1위로 회복했습니다. 하지만 다른 문항의 순위 변화 때문에 전체 뉴스 Recall은 **2/6으로 그대로**였습니다. 즉 기간 필터 문제 하나는 고쳤지만 뉴스 검색이 충분히 좋아졌다고 말할 근거는 아닙니다.

이 실행에서는 실제 실패가 2건 있었습니다. 특히 `h-na-09`는 삼성전자 수치를 애플에도 그대로 적용한 허위 비교 답변을 냈고 Solar Judge가 통과시킨 **실제 false positive**였습니다. 이 고위험 금융정보 무결성 결함이 다음 종목 문맥 안전장치(PR #76)로 이어졌습니다.

### 8-12. 다른 회사 데이터로 답하는 위험 차단 (PR #76)

**문제**: Phase 10 `h-na-09`에서 화면 선택 종목 문맥과 질문 속 다른 종목이 충돌할 때, 삼성전자 수치를 애플에도 적용한 허위 비교 답변이 실제로 나왔습니다. 서비스 가용성·CI/CD·production 뉴스 smoke는 정상이었지만, 이는 고위험 금융정보 무결성 결함입니다.

**검증**: 안전 테스트 53개, 전체 회귀 576개 통과. 이후 실제 운영 환경에서도 확인했습니다.

**한계**: PR #76 이후에는 40문제·120문제를 다시 실행하지 않았습니다. 따라서 안전장치 배포 뒤의 전체 평가 점수는 없습니다.

## 9. 왜 97.5%를 RAG 정확도라고 하면 안 되는가?

이유가 **4개** 있습니다. 하나만 있어도 충분한데 4개가 겹칩니다.

### 이유 1 — 재는 대상이 다릅니다

97.5%는 **"형식 조건 통과율"**입니다. 통과 조건 11개를 코드에서 직접 확인했는데, 거기에 **검색 성공이 아예 없습니다.**

| 통과 조건에 있는 것 | 통과 조건에 **없는** 것 |
|---|---|
| 필요한 기능 호출 | **뉴스 검색 성공 여부** |
| 기능 조건 정확도 | **뉴스 Recall@K** |
| 숫자 정확도 | **출처 coverage** |
| 기간 정확도 | **Tool 성공/실패 상태** |
| 제외 조건 준수 | **AI 채점관의 grounded 판정** |
| 다른 회사 미혼입 | |

**같은 실행에서 뉴스 검색은 33.33%였습니다.** 검색이 3분의 1만 성공한 실행이 형식 조건은 97.5% 통과한 것입니다.

### 이유 2 — 같은 문제를 다시 푼 것입니다

Phase 8에서 쓴 40문제를 그대로 다시 썼습니다. 결과 파일에 `"post_fix_same_holdout_regression"`이라고 명시돼 있습니다.

### 이유 3 — Tool이 실패해도 통과할 수 있습니다

Phase 8 홀드아웃이 극단적 증거입니다. **실제 실패가 31건인데 형식 통과율은 85%**였습니다.

### 이유 4 — 40문제뿐입니다

1문제가 2.5%p입니다. `h-fin-20` 하나가 97.5%와 100%를 가릅니다. 그리고 그 하나는 **질문이 모호했던 것**입니다.

### ✅ 이렇게 말하세요

> "수정 후 **동일 40문항 회귀 테스트**에서 **자동 형식 조건 통과율**이 85%에서 97.5%로 올랐습니다. 이건 RAG 정확도가 아니고 일반화 성능도 아닙니다. 같은 실행에서 뉴스 검색 정확도는 33.33%입니다."

## 10. 뉴스 Recall 33.33%는 무엇을 뜻하는가?

**뉴스 6문제 중 2개만 정답 사건을 찾았다**는 뜻입니다.

"Recall@K"는 **"정답 자료가 검색 결과 안에 들어왔는가"**입니다. 시험에서 "정답이 보기 안에 있었나"를 재는 것과 비슷합니다.

**6문항의 실제 내역**:

| 문항 | 질문 | 결과 | 원인 |
|---|---|---|---|

## 12. 발표용 핵심 흐름 5단계

**1단계 — 문제 인식**
"AI가 그럴듯하게 답하는 것과 정확한 자료로 답하는 것은 다릅니다. 실제로 재보니 연간 실적 대신 3분기 값을 말하고, 회사 이름을 지어냈습니다."

**2단계 — 측정 도구 만들기**
"DB 원본에서 정답을 유도해 160문항 시험지를 만들고, 120개는 연습용, 40개는 최종 시험용으로 분리했습니다. 정답 숫자는 일부러 적지 않고 채점할 때 DB에서 다시 읽게 했습니다."

**3단계 — 반복 측정과 수정**
"개발셋에서 4번 시험을 쳤습니다. 숫자 정확도 73.7% → 100%, 기간 정확도 71.1% → 100%. 도중에 **채점 코드 자체의 결함 2개**를 찾아서, 리포트 검색이 실은 93.3%였음을 밝혀냈습니다."

**4단계 — 최종 시험과 정직한 실패**

**5단계 — 원인 규명과 개선**
"저장된 기록만으로 원인을 추적해 입력 검증 오류를 규명하고 관측성을 추가했습니다. 같은 문제 회귀에서는 형식 통과율이 97.5%였지만, 뉴스 Recall은 33.33%에 머물렀고 실제 실패 2건도 남았습니다. 그중 다른 회사 수치를 적용한 허위 비교를 Solar Judge가 통과시킨 사례는 종목 문맥 안전장치(PR #76)로 별도 차단했습니다. **모두 동일 문항 회귀이지 일반화 성능이 아닙니다.**"

## 13. 3분 설명

우리는 주식 정보를 실제 DB 자료에 근거해 답하는 AI를 만들었습니다. 문제는 "잘 되는 것 같다"를 증명할 수 없다는 것이었습니다.

그래서 DB 원본에서 정답을 유도해 **160문항 시험지**를 만들었습니다. 중요한 건 **AI가 낸 답을 정답으로 쓰지 않은 것**입니다. 재무 숫자는 정답을 아예 적지 않고, 채점할 때 DB에서 다시 읽어 비교하게 했습니다. 사람이 옮겨 적으면 오타가 정답이 되니까요. 120문항은 고치는 데 쓰고, 40문항은 마지막에 한 번만 풀도록 봉인했습니다.

개발셋에서 네 번 시험을 쳤습니다. 처음엔 120문제 중 42개만 무결점이었습니다. 기능 조건 오류, 뉴스 검색 날짜 경계 버그, 공시 정렬 문제를 차례로 고쳐 숫자·기간 정확도를 100%까지 올렸습니다.

여기서 **가장 배운 게 많았던 순간**이 있습니다. 검색 점수가 계속 0%로 나와서 조사해 보니 **채점 코드가 틀렸습니다.** 정답을 완벽히 맞힌 문항을 계산에서 빼버리고, 1등 판정을 실제 순위가 아닌 알파벳순으로 하고 있었습니다. 고쳐보니 리포트 검색은 실은 **93.3%**였습니다. 제품이 아니라 **자를 의심해야 했던 것**입니다.

개발셋 97.44%에서 코드를 동결하고 40문제를 처음 풀었습니다. **85%**가 나왔습니다. 그런데 더 심각한 걸 발견했습니다 — **실제로는 31건이 Tool 오류**였는데, 통과 조건이 "기능을 불렀는가"만 보고 "성공했는가"를 안 봐서 6건만 실패로 집계됐던 것입니다. 우리는 이걸 숨기지 않고 "85%를 응답 성공률로 해석하면 안 된다", "제품 성능 완료 판정 미완료"로 기록했습니다. 점수를 본 뒤에는 코드도 정답도 고치지 않았습니다.

그다음 저장된 기록만으로 원인을 파헤쳤습니다. AI가 `순이익`이라고 썼는데 허용값은 `당기순이익`이어서 입력 검증 오류가 났고, 그 오류가 형식에 맞지 않게 처리돼 "알 수 없음"으로 기록됐던 것입니다. 오류 36건은 원인을 확정할 수 없어서 **추측 수정을 하지 않고** 다음에 잡을 수 있도록 로그를 심었습니다.

수정 후 같은 40문제를 다시 풀어 **자동 형식 조건 통과율 97.5%**가 나왔습니다. **다만 같은 문제를 다시 푼 것이므로 일반화 성능이 아닙니다.** 같은 실행에서 **뉴스 검색은 33.33%**였고, 기간 정책 수정 뒤 `h-news-22`는 회복했지만 전체 Recall은 그대로였습니다. 또 삼성전자 수치를 애플에 적용한 허위 비교 답변을 Solar Judge가 통과시킨 실제 false positive가 확인되어, 이후 종목 문맥 안전장치(PR #76)를 추가했습니다. PR #76 이후에는 전체 평가를 다시 실행하지 않았습니다.

결론적으로 기능 선택·출처 정직성은 강점이지만, **뉴스 검색·종목 정보 무결성·일반화 증거에는 한계가 남았습니다.**

## 14. 1분 설명

주식 정보를 DB 자료에 근거해 답하는 AI를 만들고, 그게 정말 맞는지 재기 위해 DB에서 정답을 유도한 **160문항 시험지**를 만들었습니다. 120개는 고치는 데 쓰고 40개는 봉인했습니다.

개발셋에서 네 번 시험을 치며 숫자·기간 정확도를 100%까지 올렸고, 도중에 **채점 코드 결함**을 발견해 리포트 검색이 실은 93.3%였음을 밝혔습니다.

봉인한 40문제에서 **85%**가 나왔는데, 실제로는 31건이 Tool 오류였고 통과 조건이 그걸 안 보고 있었습니다. 원인을 추적한 뒤 같은 40문항 회귀에서 **97.5%**가 나왔습니다. **단 같은 문제를 다시 푼 회귀 결과이고, 같은 실행에서 뉴스 검색은 33.33%입니다.** 이 회귀에서는 타 회사 수치를 적용한 허위 비교를 Solar Judge가 통과시킨 사례도 확인돼, 이후 종목 문맥 안전장치를 추가했습니다.

강점은 기능 선택 100%·출처 조작 0건이고, 약점은 뉴스 검색·타 종목 답변 안전성·일반화 증거 부재입니다.

## 16. 예상 질문 10개와 정직한 답변

**Q1. 97.5%가 RAG 정확도인가요?**

아닙니다. **자동 형식 조건 통과율**입니다. 통과 조건 11개에 검색 성공 여부가 없습니다. 같은 실행에서 뉴스 검색은 33.33%입니다. 게다가 이건 Phase 8에서 쓴 **같은 40문항을 다시 푼 회귀 결과**라 일반화 성능도 아닙니다.

**Q2. 사람이 라벨링한 데이터인가요?**

아닙니다. **DB 원본에서 결정적으로 유도하고 Claude Code/Codex가 대조 검증한 데이터**입니다. 사람 평가 양식은 만들었지만 점수 칸이 전부 비어 있고, 뉴스 동등 사건 승인 파일에도 승인자가 `"agent-assisted manual review"`로 기록돼 있습니다. 다만 정답은 검증 가능합니다 — 24개 항목 검증을 통과하고, 일부러 틀린 값을 심으면 검증기가 잡아냅니다.

**Q3. AI가 만든 정답으로 AI를 채점한 거 아닌가요?**

아닙니다. 정답은 전부 DB 테이블 행에서 나왔습니다. 특히 재무 숫자는 **정답을 라벨에 적지 않고** 채점할 때 `FactsService`로 DB를 다시 읽습니다.
단, **정직하게 짚어야 할 부분**이 있습니다. 그 재조회가 **Agent가 쓰는 것과 같은 Tool 경로**를 씁니다. 따라서 그 경로에 버그가 있으면 정답과 답변이 함께 움직입니다. 이 경로의 독립성은 보장되지 않습니다.

**Q4. 85%에서 97.5%로 올랐다는 건 성능이 개선된 거 아닌가요?**

관측된 Tool runtime 오류는 줄었습니다(Phase 8의 오류 36건 → Phase 10 Tool status error 0건). 하지만 Phase 10에는 실제 실패 2건이 남았고, **같은 문제를 다시 푼 것**이므로 "처음 보는 문제에서도 그럴 것"이라는 증거는 아닙니다. 결과 파일에 `phase10_product_fix_same_holdout_final_regression`으로 분류가 박혀 있습니다.

**Q5. 그럼 일반화 성능은 얼마인가요?**

**측정되지 않았습니다.** 유일한 블라인드 수치는 Phase 8의 85%인데, 그 실행은 Tool 경로 장애가 지배했습니다. 제대로 답하려면 **새 문항 40개를 만들어 다시 봉인 시험**을 해야 합니다.

**Q6. 뉴스 검색 33.33%는 왜 그렇게 낮나요?**

6문항 중 2개만 맞혔습니다. 초기 기록에서는 **3건이 검색 엔진 성능이 아니라 날짜 필터** 문제였습니다. 질문에 기간 표현이 없는데 AI가 "최근"(3일)을 붙여서 며칠 전 사건이 필터에서 잘렸고, PR #75에서 사용자가 말한 기간만 쓰도록 고쳤습니다. 이후 Phase 10 동일 문항 회귀에서 `h-news-22`는 회복했지만 다른 문항의 순위 변화로 전체 Recall은 **여전히 33.33%(2/6)**였습니다. 남은 검색 미적중은 원인 계층을 모두 확정하지 못했습니다.

**Q7. 환각은 없나요?**

**완전히 없다고 말할 수 없습니다.** 회사명 환각은 실제로 관찰됐고, 종목코드는 맞게 쓰면서 "삼성전자(005380)"처럼 이름을 지어낸 사례가 있었습니다. 또 Phase 10 `h-na-09`에서는 삼성전자 수치를 애플에 적용한 허위 비교를 Solar Judge가 통과시킨 실제 false positive가 확인됐습니다. 이 때문에 PR #76에서 선택 종목·질문 종목·Tool·출처의 일치 검증을 추가했지만, **PR #76 이후 평가셋 전체 재측정은 하지 않았습니다.**

**Q8. 채점 기준을 유리하게 만든 건 아닌가요?**

오히려 반대 방향으로 갔습니다. **채점기 결함 2개를 스스로 찾아 고쳤고**, 그 결과 필수 기능 호출률을 손으로 재계산해(125/127) 공식 값과 일치함을 확인했습니다.
또 `grounded`(근거에 부합하는가)라는 지표를 **일부러 통과 조건에서 뺐습니다.** AI 채점관이 출처의 제목·날짜만 보고 본문·숫자는 못 보기 때문에 신뢰도가 제한적이라고 판단했습니다.
반대로 **관대한 부분도 솔직히 말씀드리면** 있습니다. 1조 이상 금액은 조 단위 반올림으로 ±0.5조까지 통과하고, 단위 정확도는 "원"·"조"·"억" 중 하나만 있으면 통과합니다.

**Q9. 특정 문제에 맞춘 하드코딩은 없나요?**

없습니다. 이걸 명시적으로 검증했습니다. Phase 10 수정 코드는 **시간 표현만** 검사하고 홀드아웃 문항 번호·뉴스 사건 번호·회사명 목록·인물명·특정 날짜를 참조하지 않습니다. PR #76도 애플 전용 예외 없이 기존 지원 종목 목록만 재사용합니다. 개발셋 97.44%에서 **일부러 코드를 동결**한 것도 100%를 억지로 맞추려다 꼼수를 넣지 않기 위해서였습니다.

**Q10. h-fin-20 하나 때문에 100%가 아닌 건데, 그건 AI 잘못인가요?**

아닙니다. **평가 데이터의 한계입니다.** "두산에너빌리티 2025년 3분기 영업이익"이라는 질문에 Tool은 **누적값 5,506억**을, 정답은 **분기 단독 1,370억**을 기준으로 삼았습니다. 둘 다 타당한 해석입니다. 질문이 모호했던 것이고, **결과를 본 뒤 정답을 고치지 않았습니다** — 고치면 그 점수는 의미가 없어지니까요.

## 18. 이 프로젝트에서 가장 자랑할 만한 것

점수가 아니라 **태도**입니다. 발표에서 이 세 가지를 강조하면 좋습니다.

1. **낮은 점수를 숨기지 않았습니다.** 홀드아웃 85%를 받고 "실제로는 31건이 실패했다", "제품 성능 완료 판정 미완료"라고 기록했습니다. 그리고 점수를 본 뒤 코드·정답·채점기를 고치지 않았습니다.

2. **자기 자를 의심했습니다.** 검색 점수가 0%로 나올 때 제품을 고치는 대신 **채점 코드를 감사**했고, 결함 2개를 찾아 리포트 검색이 실은 93.3%였음을 밝혔습니다.

3. **모르는 것을 모른다고 적었습니다.** Tool 오류 36건의 원인을 확정할 수 없어서 **추측 수정을 하지 않았습니다.** 대신 다음에 잡을 수 있도록 로그를 심었습니다. `h-news-25`도 원인 계층을 증명할 데이터가 없어 손대지 않았습니다.
