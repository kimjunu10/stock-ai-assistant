# Phase 7 결함 — 사건 후속 질문이 다른 기간을 사용함

브랜치: `fix/phase-7-exit-gate` · 기준: `main`(4ae8965)

## 1. 증상과 재현

1. "이재용과 젠슨 황 관련 최근 뉴스를 정리해줘." → 뉴스 카드 다수 반환
2. "그 뉴스 이후 주가가 어떻게 됐어?"
3. 특정 사건 발표일이 아니라 **최근 1개월 수익률**로 답변

운영 API에서 2번 질문의 뉴스 카드가 서로 다른 사건 7건(엔비디아 본사 회동 / AI 서밋 악수 /
AI 포럼 자문위원 위촉 등)임을 확인했다. 즉 "그 뉴스"가 가리키는 대상이 애초에 확정 불가능한
상태였는데도 시스템이 답을 만들어냈다.

## 2. 근본 원인 (4계층 복합)

| # | 계층 | 원인 |
|---|---|---|
| 1 | Tool 입력 계약 | `CalculateEventReturnInput.event_date`가 **선택값**이었고, 없으면 `lookback` 기간 수익률로 정상(`ok`) 응답했다. 하나의 Tool이 "사건 전후"와 "일반 기간"을 겸해 대체가 구조적으로 열려 있었다. |
| 2 | 요청 계약 | 직전 응답의 사건 식별자·발표일을 다음 요청에 싣는 경로가 **없었다**. `context_source_id`는 있으나 발표일이 없어 사건 기준 계산 자체가 불가능했다. |
| 3 | 프롬프트 | "기간이 없으면 최근 1개월(lookback=\"1m\")을 기본으로 주가 Tool 을 호출한다"는 지시가 사건 후속 질문에도 적용됐다. |
| 4 | 최종 검증 | 검증기에 사건 근거 검증이 없었다. 일반 기간 수익률을 "그 뉴스 이후"로 표현해도 통과했다. |

1번이 직접 원인, 2·3번이 유인, 4번이 최종 차단 실패다.

## 3. 지시가 가정한 구조 vs 실제 코드 구조

| 항목 | 지시의 가정 | 실제 저장소 | 선택한 구현 위치 | 선택 이유 |
|---|---|---|---|---|
| 사건 확정 로직 | 별도 사건 해석 서비스 | 없음 | `app/agent/event_reference.py` (신규) | Agent 계층의 순수 판정 함수. 기존 서비스에 대화 상태를 넣지 않고 요청 단위로만 동작 |
| 사건 문맥 전달 | 대화 저장 시스템 | 서버 대화 상태 없음(`QaRequest.history`는 Agent에 미전달) | `QaRequest.event_context` / `selected_event_id` | 전체 대화 저장 시스템을 만들지 않고, 직전 응답과 사용자가 고른 사건만 요청에 싣는 최소 변경 |
| 사건 전후 계산 | 신규 계산 계층 | `StockPriceService.get_event_return`(대칭 ±N거래일)만 존재 | 같은 서비스에 `get_event_window_return` 추가 | 수익률 계산 단일 지점 원칙 유지. 기존 메서드는 다른 계약(대칭 window)이라 보존 |
| 사건 근거 검증 | 신규 검증기 | `app/agent/validator.py` 존재 | 같은 파일에 `validate_event_grounding` 추가 | 중복 검증기를 만들지 않고 기존 검증 파이프라인에 편입 |
| 런타임 사건 문맥 | 신규 컨텍스트 | `QaRuntimeContext` 존재 | 같은 dataclass에 필드 추가 | 중복 문맥 객체 금지 |

**영향 범위**: 백엔드 `/qa`·`/qa/stream` 요청 스키마(비파괴적 추가), 주가 Tool 계약(파괴적 —
아래 4절), 프롬프트, 검증기. 프런트는 기존 요청으로도 계속 동작하며(사건 문맥 미전송 시
"사건을 특정할 수 없음"으로 안전 응답), 사건 후속 정확성을 얻으려면 `event_context` 전송이 필요하다.

## 4. 변경한 계약

### 4.1 `calculate_event_return` (파괴적 변경)

- `event_date` **필수**. `lookback` 인자 **제거** → 일반 기간 대체 경로가 입력 스키마 수준에서 사라짐
- 발표일은 **서버 문맥에서만** 온다. Agent가 넘긴 `event_date`는 무시된다(날짜 추정 차단)
- 사건 미확정/여러 사건이면 Tool이 계산을 **거부**(`no_data`)하고 후보를 돌려준다
- 결과: 발표 전 마지막 확정 거래일 종가 기준, 발표 후 **1·3·5거래일** 종가·수익률.
  확정되지 않은 지평은 만들지 않는다. 발표 후 거래일이 하나도 없으면 `no_data`(`has_post_data=false`)

### 4.2 사건 확정 규칙 (`event_reference.py`)

1. 사용자가 직접 선택한 사건
2. 서로 다른 사건이 정확히 1개(같은 종목·같은 발표일·같은 제목의 기사 여러 건은 **사건 하나**로 클러스터)
3. 그 외에는 자동 확정하지 않고 제목·날짜 후보로 되묻는다

발표일을 확인할 수 없는 사건은 `resolved`로 승격하지 않는다(날짜 추정 금지).

### 4.3 요청 계약 (비파괴적 추가)

`QaRequest.event_context: list[EventContext]`, `QaRequest.selected_event_id`.
`EventContext`는 `event_id`(필수)·`stock_code`·`published_at`·`title`·`source_type`·`user_selected`.
값은 직전 응답의 Tool 결과 또는 사용자가 고른 카드에서 그대로 온다 — 답변 텍스트를 파싱해 채우면 안 된다.
서버는 대화별로 사건을 보관하지 않으므로, 초기화된 대화의 이전 사건 문맥은 자동으로 남지 않는다.

### 4.4 최종 검증 (§6)

"이 뉴스 이후 / 발표 후 / 사건 전후"류 주장 + 등락 표현이 함께 있으면 사건 근거를 요구한다.
근거가 없으면 검증 실패로 기록하고, 숫자를 고치지 않고 실제 상태에 맞는 안전 답변으로 **전환**한다
(사건 특정 불가 / 여러 사건 선택 필요 / 발표 후 거래일 없음 / 계산 결과 없음). 잘못된 기간으로 만든
`event_return` 시각화도 함께 제거한다.

## 5. 함께 수정한 직접 관련 결함

같은 호출 경로에서 발견한 검증기 오탐 3건(모두 회귀 테스트로 고정):

| 결함 | 증상 | 수정 |
|---|---|---|
| 날짜 오탐 | 사건 후보를 날짜와 함께 되묻는 답변의 `2026-07-25`가 "근거 없는 재무 숫자"로 검증 실패 | 검증 전 날짜 표기(ISO·한국어) 제거 |
| 종목코드 오탐 | "종목 코드 999999는 존재하지 않습니다"가 숫자 주장으로 오탐 | `종목 코드 NNNNNN`·`0`으로 시작하는 6자리를 제외(6자리 가격은 계속 검사) |
| 뉴스 수치 오탐 | 기사에 실린 지수 등락률(4.25% 등)이 재무 Tool 근거 부재로 오탐 | 뉴스·공시 문서 근거(`has_documents`)를 정당한 출처로 인정 |

## 6. 수정하지 않고 기록만 하는 항목

- `StockPriceService.get_event_return`(대칭 ±N거래일)은 현재 어떤 Tool도 쓰지 않는다.
  제거는 구조 변경이라 이번 범위 밖 — 사용처 없음만 기록한다.
- 뉴스 사건 클러스터링 품질(같은 사건이 여러 `event_id`로 갈라지는 경우)은 수집 파이프라인
  영역이다. 이번 변경은 전달된 문맥 안에서 제목·날짜·종목으로 재클러스터링해 완화만 한다.
- 증권사명 환각(게이트 9·10번에서 관측)은 기존 sanitize 계층이 문장 제거로 처리하고 있다.
  리포트 검색 품질 개선은 이번 오류와 무관하다.
- `test_feature_flag_off_returns_none`은 로컬 `.env`의 `AGENT_ENABLED=true`에 의존해
  실패한다. `main`에서도 동일하게 실패하는 기존 문제이며 이번 변경과 무관하다.
